# Reviewed retention actions — Creation and listing

Project: StreamRetain

Task: E4-02 — Action creation and listing, issue #24

Parent epic: #12 — Retention action workflow

Sprint: Sprint 4 — November 16–29, 2026

Status: implemented and locally verified; publication, CI evidence
and final acceptance review remain pending.

## Purpose

Allow the retention manager to review a suggestion, edit its proposed
follow-up and rationale, explicitly save it and retrieve saved actions.

Saving an action records a proposal.
It does not execute an intervention or demonstrate improved retention.

All customer observations used by this application are synthetic.

## Scope

This task implements:

- Persistent storage for proposed retention actions.
- Backend validation of submitted fields.
- Creation from a currently applicable suggestion.
- Listing of saved actions.
- An Angular review-and-save form.
- Explicit loading, empty-list, success and error states.
- Automated tests and manual browser verification.

Action-status updates remain separate work under E4-03, issue #25.

No customer messaging, payment changes or subscription changes
are performed.

## Data model

Actions are stored in the PostgreSQL `retention_action` table.

| Field | Storage type | Meaning |
|---|---|---|
| `id` | UUID | Unique identifier generated by the backend |
| `created_at` | Timestamp with time zone | Creation time generated by the backend |
| `observation_month` | Date | First day of the observation month |
| `plan` | Nullable text | Original subscription-plan scope |
| `proposed_action` | Text | Reviewed follow-up proposal |
| `rationale` | Text | Reviewed explanation for the proposal |
| `rule_id` | Text | Identifier of the source rule |
| `rule_version` | Integer | Version of the source rule |
| `status` | Text | Initial value is `Proposed` |

The backend generates identifiers using UUIDs and creates timezone-aware
timestamps in UTC.

The interface displays creation dates explicitly in UTC.

### Constraints

The table requires:

- A first-of-month observation date.
- A valid plan or null.
- Nonblank proposed action text of at most 1,000 characters.
- Nonblank rationale text of at most 3,000 characters.
- A nonblank rule identifier of at most 100 characters.
- A positive rule version.
- A recognized status.

The database recognizes these statuses:

- `Proposed`
- `In Progress`
- `Completed`
- `Dismissed`

E4-02 creates actions only with `Proposed`.
It does not expose status updates.

### Subscription-plan scope and All plans

At storage and response level, `plan: null` represents All plans.

The current creation API accepts only `Basic`, `Standard` or `Premium`,
because the implemented suggestion rule produces plan-specific proposals.

Selecting All plans on the dashboard does not make a Premium suggestion
an All plans action.

For example:

- Dashboard selection: September 2026, All plans.
- Reviewed suggestion: Premium.
- Saved action context: September 2026, Premium.

Creating an All plans action is not supported by the current rule.

### Multiple proposals for one segment

There is no unique constraint on observation month and plan.

Several distinct proposals may concern the same segment.

Customer-month uniqueness must not be reused as action uniqueness.

### Preservation of existing data

The initialization command creates missing tables using the shared
SQLAlchemy metadata.

It does not delete customer or customer-month records.

This initialization is not a general schema migration system:
creating missing tables does not alter an existing table definition.

## Creation API

Endpoint:

`POST /api/retention-actions`

The request contains only reviewed fields.

| Field | JSON type | Validation |
|---|---|---|
| `observation_month` | String | Valid `YYYY-MM-DD` date, first day of month |
| `plan` | String | Exactly `Basic`, `Standard` or `Premium` |
| `proposed_action` | String | 1–1,000 characters after trimming outer whitespace |
| `rationale` | String | 1–3,000 characters after trimming outer whitespace |
| `rule_id` | String | Recognized rule identifier, maximum 100 characters |
| `rule_version` | Integer | Supported positive rule version |

Blank text is rejected.
Null characters in submitted text are rejected.
Unexpected fields are rejected.

Clients cannot supply `id`, `created_at` or `status`.
Even submitting `status: "Proposed"` is rejected as an unexpected field.

Current source rule:

- Identifier: `PLAN_RATE_ABOVE_OVERALL`
- Version: `1`

### Illustrative request

This example is not a separate recorded execution.

```json
{
  "observation_month": "2026-09-01",
  "plan": "Premium",
  "proposed_action": "Investigate possible reasons for cancellation requests in the September 2026 Premium cohort.",
  "rationale": "Premium has 9 cancellation requests among 43 customers, compared with 19 among 100 customers across all plans. This is a proposal for investigation, not evidence of causation.",
  "rule_id": "PLAN_RATE_ABOVE_OVERALL",
  "rule_version": 1
}
```

### Eligibility check

Before inserting an action, the backend reads the selected month's
plan comparisons and evaluates the suggestion rule.

The submitted plan, rule identifier and version must match an
applicable suggestion.

A previously displayed suggestion may no longer be applicable if
the underlying observations have changed.

In that case, creation is rejected with HTTP 409.

The backend validates eligibility, but cannot prove that a person
actually reviewed the suggestion.

### Successful creation

A successful request returns HTTP 201 with the saved action:

- All accepted reviewed fields.
- Backend-generated identifier.
- Backend-generated creation timestamp.
- Status `Proposed`.

Creation runs inside a database transaction.
The endpoint returns success only after the transaction completes.

### Creation errors

| Situation | Response |
|---|---|
| Missing, invalid or unexpected fields | HTTP 422 |
| No matching current suggestion | HTTP 409 |
| Database configuration or database-operation failure handled by the endpoint | HTTP 503 |

A failed response must not be displayed as successful creation.

## Listing API

Endpoint:

`GET /api/retention-actions`

Response structure:

```json
{
  "actions": []
}
```

The array contains saved action objects when records exist.

The initial implementation lists all saved actions.
It does not apply the dashboard's month and plan filters.

### Stable ordering

Actions are ordered by:

1. `created_at` descending.
2. `id` descending when creation timestamps are equal.

This provides a deterministic display order.

The identifier tie-breaker is not an additional business-priority rule.

### Listing errors

A handled database failure returns HTTP 503.

The interface distinguishes a failed request from a successful
request returning an empty list.

An unavailable database must not be presented as proof that
no actions exist.

## Review form behaviour

Displaying a suggestion does not create an action.

The manager must:

1. Click `Review proposal`.
2. Review the month, plan, rule and version.
3. Review or edit the proposed action and rationale.
4. Click `Save proposal`.

The form clearly displays the context being saved.

### Fixed draft context

Opening a form copies the suggestion's context into a draft.

Changing dashboard filters does not silently change:

- The draft's observation month.
- Its subscription plan.
- Its source rule and version.
- The manager's edited text.

Only one review draft can be open at a time.

The existing draft must be closed or successfully saved before
another suggestion can replace it.

The action panel remains separate from the dashboard result-loading
lifecycle.

Changing dashboard filters does not cancel a pending action save.

### Pending save

While a save is pending:

- Repeated submission is prevented.
- Form controls are disabled.
- Closing the draft is prevented.
- A pending-state message is displayed.

These controls reduce accidental repeated clicks.
They do not provide server-side idempotency.

### Confirmed success

After a confirmed HTTP 201 response:

- The draft is closed.
- Its input fields are cleared.
- A success message is displayed.
- The saved-action list is refreshed.

If the subsequent list refresh fails, the interface may show both
a confirmed-save message and a list-loading error.

These refer to different requests.
A list-refresh failure does not reverse a confirmed save.

### Failed or uncertain save

After a failed save:

- The form remains open.
- Entered text is preserved.
- No success message is displayed.
- No automatic POST retry is performed.

For an uncertain outcome, the interface instructs the manager to
refresh saved actions before trying again.

A request may have committed even if its response was lost.
Automatically repeating that request could create another action.

The implementation does not guarantee duplicate prevention across
manual retries, browser sessions or simultaneous clients.

## Saved-action display

Each saved action displays:

- Proposed action text.
- Original observation month and plan.
- Rationale.
- Rule identifier and version.
- Status.
- Creation date in UTC.
- Unique identifier.

Changing dashboard filters does not rewrite these saved values.

Later changes to suggestion rules do not automatically update
previously saved rule identifiers, versions or text.

## Limitations

- The application remains a local educational prototype.
- Authentication and multi-user permissions are outside this task.
- Actions are proposals, not executed interventions.
- Saving does not establish improved customer retention.
- Customer observations are synthetic.
- No causal or statistical-effectiveness claim is made.
- Status updates remain under issue #25.
- Editing or deleting saved actions is outside this task.
- The initial list has no pagination.
- Server-side idempotency is not implemented.
- Manual retries can create additional actions.
- Current creation supports plan-specific suggestions only.
- The backend checks current eligibility at save time.
- A saved action does not contain a separate structured snapshot
  of all counts used when its draft was opened.
- The editable rationale is reviewed text, not an immutable audit
  record of the source observations.
- No additional isolation mechanism is implemented to freeze
  observations across dashboard display, review and creation.
- UI refinement remains under issue #26.
- Activity-based filtering remains deferred under epic #11.
